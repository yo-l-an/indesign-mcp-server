# CLAUDE.md

This repository is an MCP server that lets an agent drive Adobe InDesign.

## Correcting an InDesign document with the server

Read `GUIDE.md` before the first change: it is the workflow to follow (scope → `prepare_edit` → surgical change → `review_compare` → close), with page addressing, backups and saving. Agents outside this repository get the same file through the `get_usage_guide` tool.

## Working on the server

- `NOTES.md` (git-ignored) is where agents using the server record bugs, wanted features, better ways and the local fixes they made (`add_improvement_note`). When one is handed over: implement each entry properly (or decline it), and port local fixes as real changes with tests rather than copying them.
- `GUIDE.md` is served to agents verbatim: update it with every tool change or fix, and edit it with the `writing-for-agents` skill (steps with completion criteria, positive phrasing, one source of truth).
- Every tool lives in a `tools/*-tools.js` module: its definition (schema + `modifies: true | false`, plus `paths` / `destructive` / `overwrites` for files and confirmations, applied by `lib/policy.js`) and its handler sit together; `lib/registry.js` lists, validates and calls them (and runs a module's `hooks.beforeModify` before every modifying tool: the automatic snapshot of `tools/review-tools.js`), and `index.js` only wires modules, the executor and the workflow reminder. A new tool = one entry in one module.
- After changing tool schemas: `npm run docs` (README tool reference).
- After changing how review images are drawn: `npm run screenshots` (README images in `assets/readme/`, rendered offline from fixtures in `scripts/readme-screenshots.mjs`).
- Tests: `npm run test:offline` needs no InDesign. `npm test` drives a running InDesign; set `INDESIGN_APP_NAME` (e.g. `"Adobe InDesign 2027"`) when the installed version is not the default.
- `tools/source-tools.js` reads client files (`read_source_document`, `read_feedback`); `lib/feedback.js` turns PDF annotations and Word comments / tracked changes into one item list, one table and one locate (GREP search injected); readers: `lib/docx.js` (Word, on `lib/xml-lite.js`) and `lib/pdf-source.js` (PDF via `pdfjs-dist`, the only runtime dependency besides the MCP SDK).
- `tools/review-tools.js` holds the workflow tools (guide, prepare/compare, backups) and only gathers and writes: what changed is decided by `compareSnapshots` in `lib/review.js` behind a source adapter (page images, page lookup), tested with in-memory fixtures (`test/review-compare.test.mjs`); `lib/review-diff.js` holds the diff, table and image builders it uses; `lib/raster.js` anti-aliased shapes and text; `lib/png.js` the PNG codec. `lib/font-atlas.js` is generated by `scripts/build-font-atlas.py`.
- Generated ExtendScript is ES3; values enter scripts only through `jsStr` / `jsJson` / `jsNum`.
- A tool module receives only the tool context (`lib/tool-context.js`: `run`, `respond`, `resolvePath`, script builders, colour helpers), never the server, so a module can be tested on a hand-built context.
- Scripts run only through `lib/executor.js` (`ctx.run`); on macOS through a long-running JXA worker (`jxaWorkerAdapter`, ~15 ms per call; tested offline with a fake worker), falling back to one `osascript` per call. Each round trip used to cost ~200 ms, so a tool should do its InDesign work in as few scripts as possible. A script reports a failure by `throw new Error(...)`, never by returning an error string. Offline tests inject `createExecutor({ adapter: memoryAdapter(fn) })`.
- Review files belong in `$TMPDIR/indesign-mcp-review/`, outside the repository.
